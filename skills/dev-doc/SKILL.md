# dev-doc

用户开发一个东西时，会这样跟你配合：

1. 先在对话里聊大框架，来回改很多轮。
2. 觉得差不多了，说“定了”。你把大纲写进文档。
3. 挑出一块，比如上传，说“把上传拆出来”。你给它建一个新文档。
4. 接着聊这一块，聊定了再写进去。需要的话，再往下拆。

你只管两件事：**文件夹**和**依赖**。聊什么、拆不拆、怎么拆，都听用户的，不要自己拆。

## 规则

### 1. 没说定，就不写

讨论只在对话里进行。用户说“定了”“写进去”，你才动文件。用户没说定，就当还没定。

### 2. 只写结论

文档里只写定下来的东西。不写讨论过程，不写为什么，不写被否掉的方案，这些都留在对话里。

不要这样写：“讨论后觉得分片上传比整个上传更稳，所以决定用分片，每片 5MB。”
要这样写：“分片上传，每片 5MB。”

正文按聊的顺序写，不用套模板。

### 3. 拆一次，建一个新文件夹

所有文档放在项目根目录的 `dev-doc/` 里：

```
dev-doc/
└── file-pipeline/            ← 一个开发任务
    ├── file-pipeline.md      ← 大纲
    ├── upload/               ← 用户说“把上传拆出来”
    │   ├── upload.md
    │   └── chunking/         ← 再往下拆，做法一样
    │       └── chunking.md
    └── parse/
        └── parse.md
```

- 一个开发任务一个文件夹，里面放大纲。
- 每拆一次，就在上级文档旁边建一个新文件夹。拆几层，用户说了算。
- 一个文件夹里只放一份文档，文件名跟文件夹名一样，比如 `upload/upload.md`。这样编辑器里开着好几个标签页也不会认错。所以同一个任务里，文件夹不要重名。
- 文件夹名用简短的英文小写，单词之间用短横线，比如 `upload`、`file-parse`。文档标题用用户的说法。用户没起名字，你就起一个，并告诉用户。
- 只放这些文档，不要建 README、日志之类的文件。

### 4. 每份文档开头写上级和依赖

除了大纲，每份文档都这样开头：

```markdown
# 解析

上级：[文件处理流程](../file-pipeline.md)
依赖：[上传](../upload/upload.md)
```

- **上级**：它是从哪份文档里拆出来的。大纲没有上级，开头只写标题。
- **依赖**：它要用到哪些文档里定下的东西，比如别的模块的接口、数据格式。上级不算依赖。有好几个就用“、”隔开，没有就写“依赖：无”。
- 链接都用相对路径。

下面拆出了东西的文档，在最后列出来，每个一句话：

```markdown
## 子模块

- [上传](upload/upload.md)：用户上传文件，大文件分片传，支持断点续传
- [解析](parse/parse.md)：把三种格式的文件转成统一的纯文本
```

### 5. 一件事只写一次

上级写各部分怎么配合，子模块写自己内部怎么做。子模块的细节不要在上级里再写一遍，上级里留一句话就够了。这样以后改，只用改一个地方。

### 6. 聊一个模块前，先读它的上级和依赖

先读它的上级，一级一级读到大纲，再读它依赖的文档。已经在对话里的不用再读。

这个模块管什么、不管什么，是上级定的；它怎么跟别的模块接上，是依赖里定的。不读就容易聊偏。换了新对话接着聊时，尤其要先读。

### 7. 改完一份，检查相关的文档

改完一份文档，看看跟它有关的文档还对不对：

- **上级**：上级里介绍它的那句话，还准吗？
- **子模块**：它下面的子模块，跟它现在的结论还对得上吗？
- **依赖它的文档**：在这个任务的文件夹里，搜“依赖：”那一行里有没有指向它的链接，比如 `grep -rn "依赖：.*upload/upload.md" dev-doc/file-pipeline/`。搜到的文档，看看会不会受影响。

需要跟着改的，一次全列给用户：改哪份、改什么、为什么。用户同意了再改。不要自己偷偷改别的文档：框架是用户在定，偷偷改了，文档就跟用户想的不一样了。

## 具体怎么做

### 用户说“定了”“写进去”

把对话里最新的结论写进正在聊的那份文档。

- 这个任务还没有文件夹：建 `dev-doc/<任务名>/<任务名>.md`，把大纲写进去。
- 文档已经有了：更新正文，换成现在的结论。依赖有变化，就改“依赖”那一行。

写完按第 7 条检查一遍。不用提交 git，用户要的时候会说。

### 用户说“把 X 拆出来”

1. 先确定 X 的上级，一般就是正在聊的那份文档。如果上级还没写进文档，先问用户：要不要按现在聊的结果，把上级也一起写进去？
2. 在上级旁边建 `x/x.md`，开头写标题、上级、依赖。依赖只写已经定了的，不清楚就写“无”。
3. 正文先放上级里关于 X 的那句话，等聊定了再补全。如果上级里关于 X 写了不止一句，就把这些内容搬到新文档里，上级只留一句话。
4. 在上级的“子模块”里加上 X 的链接和那句话。

这些都是拆分的一部分，不用另外问。做完告诉用户：建了哪些文件，从上级搬走了什么。

### 用户要改名、移动、合并、删除

- **改名、移动**：文件夹和文件一起改，再把指向它的链接都改掉，包括它下面子模块的“上级”、别的文档的“依赖”、上级的“子模块”列表。如果是移动，它自己和它子模块里指向外面的链接，路径也要重新算。
- **合并**：把它的内容搬进要合并到的那份文档，删掉它的文件夹，再照上面改链接。
- **删除**：先看它下面有没有子模块。有的话，先问用户这些怎么处理。删掉以后，从上级的“子模块”里去掉。

改链接是这些操作的一部分，不用另外问。做完按第 7 条检查一遍。
