# dev-doc

用户做开发时习惯这样推进：先在对话里跟你反复聊一个开发任务的大框架，聊定了写进大纲；然后说"先聊上传，拆个新文档"，拆出一个模块，再聊这个模块的小框架；需要时继续往下拆。

这个 skill 只管两件事：**文件夹**和**依赖**。怎么聊、拆不拆、拆成什么，都由用户决定，你不要自己拆。这套文档是用户和你对齐思路用的，结构得是用户脑子里的结构。

## 文件夹

所有文档放在项目根目录（通常是 git 仓库的根）的 `dev-doc/` 里：

```
dev-doc/
└── file-pipeline/            ← 一个开发任务
    ├── file-pipeline.md      ← 大纲
    ├── upload/               ← 用户说"把上传拆出来"
    │   ├── upload.md
    │   └── chunking/         ← 继续往下拆，规则一样
    │       └── chunking.md
    └── parse/
        └── parse.md
```

- 每个开发任务一个文件夹，里面放这个任务的大纲。
- 每拆一次，就在上级文档所在的文件夹里建一个子文件夹。拆几层由用户决定。
- 每个文件夹里只放一份文档，文件名和文件夹名相同，比如 `upload/upload.md`。这样编辑器里开着好几个标签页也分得清；也因此，同一个开发任务里文件夹名不要重复。
- 文件夹名用简短的英文小写，单词之间用短横线，比如 `upload`、`file-parse`；文档标题用用户的叫法。用户没给名字时由你来取，并在回复里告诉用户。
- 这些是开发任务的工作文档，不是给别人看的说明，所以不建 README、日志之类的其他文件。

## 文档格式

除了大纲，每份文档都这样开头：

```markdown
# 解析

上级：[文件处理流程](../file-pipeline.md)
依赖：[上传](../upload/upload.md)
```

- **上级**：拆出这份文档的那份文档。大纲没有上级，开头只有标题。
- **依赖**：这份文档的结论建立在哪些其他文档的结论上，比如用到了它的接口、数据格式或流程。上级不算依赖。多个依赖用"、"隔开，没有就写"依赖：无"。
- 链接都用相对路径，点得开，也搜得到。

正文只写对话里定下来的**结论**，按讨论时的结构组织，不套固定模板。讨论过程、理由、被否掉的方案都不写：讨论留在对话里，文档只放现在的定论。

有子模块的文档，在末尾列出子模块，每个一行摘要：

```markdown
## 子模块

- [上传](upload/upload.md)：用户上传文件，支持断点续传
- [解析](parse/parse.md)：把各种格式的文件转成统一的文本
```

**一件事只写在一个地方。** 上级写整体怎么拼起来，子模块写自己内部怎么做。子模块的细节不要在上级里再写一遍，上级只留那一行摘要，这样改一处就不用到处同步。

## 什么时候做什么

### 讨论中

只在对话里聊，不动文件。用户没说定，就当还没定。

### 开始聊某个模块之前

先读从大纲到这个模块的每一级上级文档，再读它依赖的文档（已经在当前对话里的不用重读）。模块的范围和约束来自上级，接口来自依赖，不读就容易聊偏。在新对话里接着聊某个模块时尤其要这样做。

### 用户说"定了""写进去"

把对话里最新的结论写进正在聊的那份文档：

- 这个开发任务还没有文件夹时，建 `dev-doc/<开发任务>/<开发任务>.md`，把大纲写进去。
- 文档已经存在时，更新正文，让它反映现在的结论；依赖变了就改"依赖"那一行。

写完做一次改动检查（见文末）。不用提交 git，用户需要时会自己说。

### 用户说"把 X 拆出来"

1. X 的上级就是 X 所属的那份文档，通常是正在聊的那份。如果上级文档还没写，先跟用户确认：是不是把上级按对话里最新的结论一起写进去。
2. 在上级文档所在的文件夹里建 `<x>/<x>.md`，开头写标题、上级和依赖。依赖只写已经定了的，不清楚就写"无"。
3. 新文档的正文先放上级里关于 X 的内容，通常就是一行摘要，等用户聊定了再补全。如果上级里关于 X 的内容不止一行，就把这些细节从上级搬过来，上级只留一行摘要。
4. 在上级的"子模块"列表里加上 X 的链接和这行摘要。

这几步都属于拆分本身，不用另外问用户。做完告诉用户建了哪些文件、从上级搬走了什么。

### 用户要改名、移动、合并或删除模块

- **改名或移动**：文件夹和文件一起改，再把指向它的链接都改过来：它子模块的"上级"、别的文档的"依赖"、上级的"子模块"列表。移动的话，它自己和它子模块里往外指的相对链接也要重新算。
- **合并**：把被合并文档的结论搬进目标文档，删掉它的文件夹，再按上面的方法改链接。
- **删除**：先看它下面有没有子模块，有就先问用户子模块怎么处理；删掉后，从上级的"子模块"列表里去掉。

改链接属于这些操作本身，不用另外问。做完跑一次改动检查，依赖了被删文档的文档会在检查里列出来。

## 改动检查

改完一份文档，检查和它相连的文档还对不对得上：

- **上级**：上级里关于它的那行摘要还准确吗？
- **下级**：它的子模块和它现在的结论还一致吗？
- **依赖它的文档**：在这个开发任务的文件夹里，搜"依赖："行里指向它的链接（比如 `grep -rn "依赖：.*upload/upload.md" dev-doc/file-pipeline/`），看这些文档的结论有没有受影响。

需要跟着改的，一次列给用户：改哪份文档、改什么、为什么。用户同意后再改。不要悄悄改别的文档：框架是用户在主导，悄悄改了，文档就和用户脑子里的框架对不上了。
